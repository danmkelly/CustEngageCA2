Additional Observations

  • Seasonal items: EP-0014 (Elderflower Cordial) and EP-0030 (Spiced Apple Chutney) are marked Seasonal. EP-0030 has an offer ("Buy one get one half price") on a seasonal item — this is valid but worth noting for offer expiry tracking.
  • Pre-order item: EP-0026 (Aged Balsamic Vinegar) is marked Pre-order. Stock of 14 units is shown. This is a valid pre-order pattern.
  • Easter eggs: The two price anomalies are explicit easter eggs with "do not correct" annotations. The chatbot respects these — it never corrects prices from the Sheet. This is the correct behaviour for this academic prototype.
  • OFF search API: The OFF search endpoint (/cgi/search.pl) rate-limits anonymous access from Cloudflare Workers. Name-based search fallback for non-matching barcodes is not viable. The barcode lookup API (/api/v2/product/{barcode}) works reliably without authentication.
Production Design

Proposed Quarantine Architecture

In a production deployment, data quality issues would be intercepted before reaching the customer-facing UX. Below is the proposed architecture. For this academic prototype, dirty data deliberately flows to the UX so the lecturer can observe chatbot behaviour with real (and intentionally problematic) data.

How it would work

  1. Ingest: Google Sheet data is fetched as today — live, on every request.
  2. Validate: Orla runs the same validation rules documented above against every row before it enters the product catalogue. Rules are configurable per field (price thresholds, barcode format, stock/availability consistency, unit normalisation, offer timing).
  3. Split: Clean products flow directly to the UX. Products with active flags are routed to a quarantine store (Cloudflare KV or D1). They do not appear in the customer-facing catalogue.
  4. Review: A human reviewer (the Emerald Pantry product owner) accesses a review dashboard. For each flagged product, they choose one of: Confirm (accept the flag, edit the Sheet), Correct (override with a corrected value), or Dismiss (false positive — the data is intentionally as-is).
  5. Persist: Dismissed flags are recorded with the reviewer's identity and timestamp. Orla does not re-raise the same flag for the same product unless the underlying data changes. This prevents review fatigue from known false positives.
  6. Release: Once reviewed, the corrected product moves from quarantine to the live catalogue. The customer never sees dirty data.

Why not in this prototype

For the CA2 academic submission, the lecturer needs to see how the chatbot handles problematic data — incorrect prices, missing OFF enrichment, stock contradictions. Quarantining this data would hide the chatbot's data-handling behaviour from assessment. The current approach — surface everything with transparency labels — is the correct design for this context.

Assignment Context

Original prompt (with minor typos corrected):

"An issue is the quality of the ingested data. I can see at least two wildly incorrect prices, 25 items that do not match the OFF database, etc. These issues are filtering all the way through to users. I do not think it is architecturally correct to burden the chatbot with data quality issues or to debate those with users. I do think there should be a separate process or agent that detects issues, places that data in quarantine (i.e., does not let it flow to the UX), flags it to a human for review, and records and respects their decision (including false-positive persistence). However, for this project it is key that the dirty data gets all the way to the UX so the lecturer can validate behaviour. So please go as far as building that agent and reporting findings on suspicious data to this page; also propose the design you would implement in production should that be required later."
