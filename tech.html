Emerald Pantry Technical Reference

Development toolchain, agent architecture, data pipeline design, and live-data evidence — the technical story behind the chatbot.

Development Environment

OpenCode & DeepSeek — the toolchain

The entire Emerald Pantry chatbot was developed using OpenCode (an AI-assisted coding environment) powered by DeepSeek (via deepseek-v4-pro). All code generation, refactoring, debugging, and deployment happened within this single toolchain. No traditional IDE was used.

Model: DeepSeek V4 Pro (via opencode-go/deepseek-v4-pro)

Interface: OpenCode CLI — file read/write, shell execution, git operations, web fetching, glob search, grep search

Deployment: git push to GitHub Pages · npx wrangler deploy to Cloudflare Workers

Evidence: All commits (see commit history) were authored by OpenCode sessions. Each commit message describes the agent-orchestrated change.

Development Methodology

The Five Innovators + QA model

The project was structured using the Five Innovators model (Victor del Rosal) — a framework for dividing innovation work across five non-overlapping specialisms, plus a dedicated QA specialist. Each agent has a defined persona file (.md) in the repository that specifies its domain, beliefs, boundaries, and skills.

Worker Endpoints

GET/POST /api/llm — Proxies chat completion requests to DeepSeek. The API key lives in a Cloudflare environment variable (npx wrangler secret put LLM_KEY). The browser never sees it.

GET /api/catalogue — Fetches the Google Sheet as CSV, parses it to JSON, returns product list. Accepts ?q= (text search) and ?category= filters. No cache — every request is a fresh Sheet fetch (see evidence below).

GET /api/enriched-catalogue — Same as above, then makes 30 parallel barcode lookups to the OFF API and merges nutritional data into each product. OFF data cached 1 hour (nutritional facts are static); Sheet data is always live.

Data Pipeline

Google Sheets → OpenFoodFacts enrichment

Google Sheets integration

The product catalogue lives at https://docs.google.com/spreadsheets/d/1fY7974AdL4rrO2gnCxcCBUFWWSkVhOi9euJI7lNjo2Q/edit. The Worker fetches it via the CSV export endpoint (/export?format=csv). A custom CSV parser handles quoted fields (product descriptions contain commas). No Google Sheets API key needed — the sheet is published and the CSV export is public.

OpenFoodFacts integration — why the barcode API, not MCP

The OFF integration uses the public product API: GET https://world.openfoodfacts.org/api/v2/product/{barcode}.json. This endpoint returns full nutritional data, allergens, Nutri-Score, NOVA group, Eco-Score, dietary flags, ingredient analysis, and product images — all from a single HTTP call with no authentication required.

Why not MCP (Model Context Protocol)? An MCP server wrapping the OFF API would add deployment complexity (a separate server process), authentication overhead, and an additional network hop for what is fundamentally a single GET request per barcode. The Worker already handles the enrichment directly — 30 parallel fetch() calls, each to a simple REST endpoint. MCP would be the right choice if the integration required multi-step tool orchestration (e.g., search → narrow → compare → enrich), but for product-by-barcode data lookup, a direct HTTP call is simpler, faster, and more maintainable.

The Worker's extractOffFields() function maps the rich OFF response to a compact enrichment object with only the fields the chatbot needs: Nutri-Score, NOVA, Eco-Score, allergens, dietary tags, nutrient levels per 100g, product image URL, and OFF categories hierarchy. This keeps the payload small for the frontend.

Live Data Evidence

How to verify live data pulls

The chatbot makes live data pulls at multiple points. Each is independently verifiable:

1. Google Sheet — zero-cache catalogue fetch

Every /api/catalogue request appends &t={timestamp} to the Google Sheets CSV URL, bypassing any CDN or browser cache. The Worker response includes Cache-Control: no-cache, no-store, must-revalidate. Browser-side, every fetch() uses {cache: "no-store"}.

Evidence Open DevTools → Network tab → filter for catalogue. You will see a request to the Worker on every page load, every search, and every filter change. The response always includes the current timestamp in the updated field. Compare this with the Google Sheet to confirm data freshness.

Evidence Change a value in the Google Sheet (e.g., a price or stock count). Type the product name in the chatbot. The new value appears immediately — no cache delay, no stale data window.

Evidence Worker code: var resp = await fetch(CATALOGUE_URL + "&t=" + Date.now()); in worker.js line 63. Response headers: "Cache-Control": "no-cache, no-store, must-revalidate".

2. OpenFoodFacts — barcode enrichment

Each product with a real barcode triggers a lookup to world.openfoodfacts.org/api/v2/product/{barcode}. The Worker makes all 30 lookups in parallel via Promise.all(). OFF nutritional data is cached 1 hour (it's static); the Google Sheet data around it is always live.

Evidence Open DevTools → Network tab → filter for enriched-catalogue. The response includes "source": "emerald-pantry + openfoodfacts". Each product with OFF data has nutriscore_grade, nova_group, allergens, image_url fields. Compare these against the OFF website: search for the barcode at world.openfoodfacts.org/product/{barcode}.

Evidence Worker code: enrichProduct() in worker.js lines 153–165. The OFF_URL constant at line 11. Cache TTL: "Cache-Control": "public, max-age=3600" (1 hour).

3. DeepSeek LLM — conversation proxy

Every user message (post-onboarding) triggers an LLM call to api.deepseek.com/v1/chat/completions. The request includes conversation history (last 20 exchanges), the Ember system prompt, and full catalogue context for the products currently in view.

Evidence Open DevTools → Network tab → filter for llm. Each user message after onboarding produces a POST to the Worker's /api/llm endpoint. The response contains the LLM-generated reply. The Authorisation header is never visible in the browser — it's injected server-side by the Worker.

Evidence Worker code: LLM proxy in worker.js lines 28–37. Key from env.LLM_KEY (Cloudflare secret). Frontend sends a plain JSON body with model, messages, temperature, max_tokens.

4. Automated test verification

The runFilterTests() function (accessible by typing test in chat) programmatically verifies all 18 filter interactions against live data. It checks that clicking "Bakery" returns exactly the number of bakery products in the live catalogue, that Clear All restores the full 30, and that all 13 filter pills toggle correctly.

Deployment

GitHub Pages + Cloudflare Workers

Frontend: Static HTML/CSS/JS served via GitHub Pages from the main branch root. Cache-control headers set via _headers file and HTML <meta> tags to prevent stale JS caching.

Backend: Cloudflare Worker (emerald-pantry-proxy) deployed via npx wrangler deploy. The DeepSeek API key is stored as a Cloudflare secret. Three endpoints handle LLM proxy, catalogue fetch, and enriched catalogue.
